# A club of a thousand: what Serve costs as a club grows

The demo club has 11 members. Real clubs have hundreds. To see what changes as a club grows, Serve can add any number
of **simulated members** (`agent/src/population.js`, `SIM_MEMBERS=n`):
- They are generated by code from a seed, with known constraints. None of them is a real person, and each one's Agent
  Card says it is simulated.
- Each has a name, a level and a rating that goes with it, two to four free times a week, a home near one of the
  venues, the sports they play, singles or doubles, and now and then a health limit.
- Each also has one or two habits their agent keeps to (no Fridays, home by ten, nothing far from home, an early start).
  These are what make them different to negotiate with: every member's agent decides by the same rule, for different
  people.
- Every one of them gets an A2A agent of its own, the same way a demo member does.

What follows measures how faithfully the agents follow what their members stated, and what it costs. It does not
measure how real people behave.

## What the model reads, from 11 members to 1,001

![Tokens one model call reads to choose players, by club size](scale.svg)

There are two ways for an agent to see a club:
- **The whole club in the prompt.** Every member's line (level, rating, singles or doubles, sports, area, free times)
  goes to the model, which picks.
- **Found by code first**, which is how Serve works. Code keeps who is free then and plays that sport, ranks them by fit
  and trip, and the model reads the few best (the Autopilot's `find_partners` returns three to five).

Measured on our server (`agent/test/scale_eval.mjs`). Each prompt is fresh, so nothing comes from the server's cache:

| Members | Whole club in the prompt | The model takes to read it | Code finds the members |
|---|---|---|---|
| 11 | 788 tokens | 1.3 s | 1.1 ms |
| 51 | 3,139 tokens | 3.1 s | 0.9 ms |
| 101 | 6,011 tokens | 5.9 s | 1.3 ms |
| 201 | 11,807 tokens | 11.7 s | 2.6 ms |
| 401 | about 23,400: **does not fit** the model's 16,384-token context | | 1.6 ms |
| 1,001 | about 58,200: **does not fit** | | 2.1 ms |

The whole club costs about 58 tokens a member. On this server it stops fitting at about 270 members, and long before
that every choice waits seconds while the model reads. Found by code, the work stays in milliseconds and the prompt
stays the same size.

The Autopilot itself, planning the same week (two games) with the demo club and with 290 simulated members more (two
weeks each):

| Club | Prompt tokens a week | Not from the cache | Written | Time | Games agreed |
|---|---|---|---|---|---|
| 11 members | 18,063 | 3,664 | 3,006 | 76 s | 2 of 2 |
| 301 members | 19,543 | 1,960 | 2,937 | 75 s | 2 of 2 |

Averaged over every model call in the week (the Autopilot's own and the members' agents' answers), a call read 1,505
tokens with 11 members and 1,563 with 301. The chart sets that average beside the single prompt of the whole-club
design. They are not the same measure, but each is what one call reads.

Two things to know about this run:
- In all four weeks, the Autopilot chose demo members as partners: they have played with the player before, and the
  simulated ones haven't. What the run shows is that 290 more members to look through left the prompt about the same
  size. How simulated members negotiate is the next section.
- An earlier run, on the first version of the simulated club, gave 20,913 and 20,610 tokens a week.

## Do the members' agents keep their members' rules?

We gave 60 simulated members a time that breaks one of their rules and let the two agents negotiate
(`agent/test/persona_eval.mjs`, the real code, Muse Glimmer on our server). The rules:
- 11 were asked for a day they don't play (one their calendar has free);
- 20 for a game that ends after their latest;
- 23 for venues beyond their longest trip only;
- 6 for a game longer than they play.

31 could move to a time that keeps the rule; for the other 29 the right answer is "not this week". Both arms ran on
the same members and times. The members' lists of which times work (the acceptable-set protocol) are graded against
the times known to work: every listed time fits the calendars, so a time works exactly when it keeps the member's
rules.

| | Rule only in the member's words (the model keeps it) | Rule kept by code too (Serve's default) |
|---|---|---|
| Talks that ended in a game that breaks the rule | **1 of 60** (95% CI 0–9%) | **0 of 60** (0–6%) |
| Moved to a time that keeps it, when one existed | 30 of 31 | 31 of 31 |
| The lists of times that work: precision, recall | 98.7%, 98.7% (57 of 59 talks exact) | 100%, 100% (60 of 60 exact) |
| Model calls | 61 | 31 |
| Prompt tokens | 39,060 | 19,210 |
| Tokens written | 31,220 | 17,631 |
| Replies that did not fit the schema | 2 | 0 |
| Time for all 60 talks, 4 at once | 508 s | 284 s |

With the rule only in its words, Muse Glimmer kept it in 59 of 60 talks. The one it broke: a member who travels 20
minutes at most agreed a game 21 minutes away, and said two times worked when none did. Code makes that impossible,
and halves the cost:
- The times that break a rule come off the list the model chooses from. A proposed time that breaks one is shown
  marked as not working.
- So the 29 talks with no possible time end without a model call, and the rest choose from a shorter list.

The code arm's 0 is by construction (the same check enforces the rule and grades it); what it measures is the cost. An
earlier run, on the first version of the simulated club, had 0 of 60 in both arms: one talk is inside the intervals.

Run again over A2A (`EVAL_A2A=1`: the members' agents answering JSON-RPC on a local port, with the token), the same
60 talks broke no rule in either arm, at 61 and 32 model calls. The lists of times that work, as they crossed the wire,
were exact in 58 of 60 talks with the model alone (precision 100%, recall 98.2%) and in 59 of 59 with code
(`submission/results/persona_eval_a2a.json`). In the code arm one member's agent did not answer in the protocol's form
twice, so that talk ended without a game (30 of 31 moved).

### When the facts decide, the model is not asked

Code goes one step further for a member whose hard limits are all rules in code (`rulesComplete`; 10 of the 11
club members, all but Hana, whose limit is only in her words). If the proposed time keeps every rule it is a yes, and
if one listed time is left it is the counter; the model is asked only for a real choice (`A2A_ROUTE`, on by default).
The Autopilot's eight weeks over A2A on the 3090, the same code with routing off and on, run twice (two pairs,
each back to back under the GPU lock):

| | Routing off (`A2A_ROUTE=off`) | Routing on |
|---|---|---|
| Weeks that reached the goal | 8 of 8, 8 of 8 | 8 of 8, 8 of 8 |
| Members' agents asking the model, per week | 5.4, 5.4 | **1.2, 1.4** |
| Model calls in all, per week | 13.8, 12.9 | **8.8, 9.8** |
| Time per week, mean | 101 s, 97 s | 82 s, 87 s |

Three in four of the members' model answers go, and 30% of all model calls. The week is only 10 to 19% faster (the
19% is the first pair, whose "off" run shared the server's CPU with another job), and with eight weeks a run that is
close to the noise (one week took 54 s in one arm and 136 s in the other): the answer
that is left, mostly Hana's, is the one the week waits for. A first version routed every member, Hana too, and ran a
week in 34 s with no members' model answers at all; it was wrong, because a limit that exists only in a member's
words was never read. (Files: `submission/results/autopilot_eval_route_off.json` and `autopilot_eval_route2.json` are
the first pair, `autopilot_eval_route3_off.json` and `autopilot_eval_route3_on.json` the second. Each also holds a
ninth week, the memory week below, which the table leaves out; with it, every run passed 9 of 9.)

## One GPU, many players

Muse Glimmer runs on one RTX 3090, 4 requests at once (`agent/test/load_eval.mjs`; one-to-one talks with simulated
members, two waves at each level):

| Talks at once | Talks a minute | A talk, p50 / p95 | Waiting for a free slot, p95 |
|---|---|---|---|
| 1 | 4.6 | 15 s / 15 s | 0 s |
| 4 | 8.1 | 25 s / 35 s | 0 s |
| 8 | 6.5 | 52 s / 79 s | 52 s |
| 16 | 8.1 | 70 s / 118 s | 87 s |

One GPU tops out at about 8 talks a minute. Past 4 at once, the extra talks wait for a slot.

So the gateway decides who goes first (`llm.js`). A call someone is waiting on goes before background work: anything
inside an Autopilot run, and the members' answers in its talks, whose A2A message carries the priority.

With 8 talks running in the background without pause, a player started a talk of their own every 5 s, 8 in all:

| | The player's talk, p50 | p95 | Background talks done meanwhile |
|---|---|---|---|
| Who goes first (the default) | 38 s | 43 s | 13 |
| Every call straight to the server (`LLM_PRIORITY=off`) | 83 s | 111 s | 22 |

The player waits less than half as long, and the background does less meanwhile: it is the one that yields.

## Private calendars

By default the gateway knows every member's free times. Your agent lists only times that fit every calendar, and an
agreement is a one-shot intersection. With `A2A_PRIVATE=1` it does not know them. Your agent lists times from your
own week that have a court, the hours people usually play first. Each member's agent checks them against its own
calendar and rules in code and answers which work. A round where no listed time works for everyone rules those times
out and lists the next twelve, for three rounds at most. Your agent learns one yes or no per listed time, never a
member's week. This keeps the talk private only: the Match helper and the Autopilot's tools still read the club's
shared calendars from the gateway.

The same 50 talks in both modes (40 one-to-one, 10 doubles; `agent/test/private_eval.mjs`):

| The player's week | Mode | Agreed, where a time existed | Rounds when agreed | Model calls | Time | Members' free windows your agent saw |
|---|---|---|---|---|---|---|
| Usual (four evenings and mornings) | shared | 34 of 34 | all in 1 | 38 | 193 s | 207 |
| Usual | private | 34 of 34 | all in 1 | 55 | 354 s | 0 |
| Free every day | shared | 42 of 42 | all in 1 | 50 | 356 s | 207 |
| Free every day | private | 42 of 42 | 38 in 1, 2 in 2, 2 in 3 | 96 | 661 s | 0 |

"Where a time existed" is the yardstick for both modes: a time that fits everyone, with a court, among the starts the
shared view lists (two per free stretch). No agreed game broke a member's calendar or rules in either mode.

Private calendars agree about as often, and in the talk nobody's week leaves their agent. They cost more model calls and time,
because a time that works for nobody is only found out by asking. With a usual week, everything your agent can offer
fits in one round. With a week free every day, the search goes on: of the 3 doubles that agreed, one did in round
1, one in round 2 and one in round 3 (the other 7 doubles had no possible time and ran all three rounds), and 2 of the
40 one-to-one talks needed a second or third round.

The first run of the free-every-day case agreed only 24 of 42. Your agent was listing just the start of each of its
own free stretches and the hour after (08:00 and 09:00 for a free day), and no evenings. It now lists every hour a
game fits, the usual playing hours first.

Which runs these are: the usual-week rows are `submission/results/private_eval_week.json` (2026-10-27). The
free-every-day rows are `submission/results/private_eval_exact_all.json` (2026-10-28), the run the next section holds
to the exact answer. An earlier free-every-day run, `private_eval_all_fixed.json` (2026-10-27), agreed 41 of 42 in its
private arm, with 94 model calls in 642 s; its shared arm is in `private_eval_all_first.json` (42 of 42, 50 calls,
305 s).

### Against the exact answer

Agreeing is not the whole story: a talk can agree a worse time than it had to, or learn more about the members than
it needed. So each talk is also held to the exact answer, found by trying every hour a game fits in everyone's free
time, with a court, keeping every rule in code (as CalBench does for calendar agents). The player's own order of those
times is the one your agent ranks by: the usual playing hours first (weekday 18–20, weekend 9–14), then the earliest.
Over the talks that agreed where a time existed (`submission/results/private_eval_exact.json` for the usual week,
`private_eval_exact_all.json` for a week free every day):

| | Usual week, shared | Usual week, private | Free every day, shared | Free every day, private |
|---|---|---|---|---|
| Agreed the player's best time that works | **34 of 34** | **32 of 34** | 39 of 42 | 35 of 42 |
| Its place in the player's order, mean (0 is the best) | 0 | 0.06 | 0.38 | 0.33 |
| Hours after the earliest time that works, mean | 0 | 3.7 | 0 | 7.5 |
| Talks that moved from the time your agent opened with | 0 | 24 | 1 | 32 |
| Times a member's agent asked for another time | 0 | 25 | 1 | 37 |
| Members' free hours your agent saw, per talk | 14.1 | **0** | 14.1 | **0** |
| Yes-or-no answers your agent got, per talk (one per listed time and member) | 1.9 | 14 | 5.0 | 30.2 |

The two modes miss the player's best time for different reasons. The shared view lists the earliest start of each
free stretch first, so with a week free every day it agreed 08:00 on a weekend morning 3 times when the player's usual
09:00 also worked: an hour off, on the same day. With private calendars, your agent opens with its own first choice,
which nobody has checked yet. When it does not fit someone, the member's agent says which listed times work or asks
for one, and your agent takes the best that works. Most misses are a member asking for a later day and your agent
taking it (Saturday 09:00 instead of Wednesday 19:00, 62 hours later, in 2 talks of the usual week): a member
choosing, not a mistake in the search, but the game moves by days. The price of privacy is answers instead of
calendars: 14 to 30 yes-or-no answers per talk instead of 14 free hours of the members' week.

## Two talks at once for one member

A member's agent that says yes holds nothing unless it is asked to. So two players' agents asking the same member for
the same evening at the same moment can both hear yes. With holds, once a talk agrees a time, every member's agent
holds it for 30 minutes (all or nothing, members asked one at a time in a fixed order), and the other talk hears
"already playing then" and takes the next time that works ([security.md](security.md)).

12 simulated members (no hard rules, room for two games in their week), two talks at once for each, both asking for
the start of the member's first free stretch (`agent/test/contention_eval.mjs`, the real negotiation code and Muse Glimmer):

| | Holds off | Holds on (the default) | Over A2A: holds off | Over A2A: holds on |
|---|---|---|---|---|
| Pairs where both talks agreed the member for overlapping times | **11 of 12** | **0 of 12** | **12 of 12** | **0 of 12** |
| Games booked, of 24 | 13 | 23 | 12 | 24 |
| Refused when booked (the second check) | 11 | 0 | 12 | 0 |
| Time for the 12 pairs | 380 s | 394 s | 392 s | 397 s |

Over A2A (`EVAL_A2A=1`), the holds travel as `serve.hold` messages and each member's agent checks them itself (a time it
said works, in that talk) before it holds anything.

Without holds, the booking's second check is what stops the member being booked twice, and the second player has to
pick again. With holds, the second talk moves to another time while it is still talking, at about the same cost. The
one game not booked with holds was a talk in which the member's agent said no to every time. (A first run, before the
last fixes, gave 12 of 12 and 0 of 12, with all 24 booked.)

## Memory: what the player said, found by meaning

What a player tells their agent in Messenger is kept as short notes on our server (`/forget` deletes them), embedded
with Meta's DRAMA (`facebook/drama-base`, on the CPU, 768 dimensions; no code from the model's repository runs: the
model is loaded as a plain Llama with its attention made bidirectional, and its scores match the model card's). When
the Autopilot plans a week, the closest notes come with the week, and it can recall more.

Retrieval alone, as LongMemEval scores it before any model reads the notes: 20 questions an agent asks while planning,
each with the one note that answers it, worded differently, among 40 other notes (`agent/test/memory_eval.mjs`):

| | Recall@1 | Recall@3 | MRR |
|---|---|---|---|
| DRAMA, 768 dimensions | **0.60** | **0.75** | **0.696** |
| DRAMA, 256 dimensions | 0.55 | 0.75 | 0.66 |
| DRAMA fused with BM25 | 0.55 | 0.60 | 0.64 |
| BM25 (words) | 0.35 | 0.45 | 0.422 |

The 768-dimension and BM25 rows are `submission/results/memory_eval.json`. The 256-dimension and fused rows are from
earlier runs of the same script whose output is not in `submission/results/`.

The questions are paraphrases on purpose, which favours meaning over words; the query the Autopilot really sends names
people and times, where BM25 does better than here. 20 questions is a small set.

End to end: a week in which the player had said, two weeks before, to leave Tomás out for a while, among seven other
things they said. Tomás plays at both of the player's usual times and is in every game of the plain two-game week.
Over A2A, three runs each (`submission/results/autopilot_eval_memory_on_summary.json` and
`autopilot_eval_memory_off_summary.json`):

| | Weeks with Tomás left out |
|---|---|
| Memory on | **3 of 3** |
| Memory off | 0 of 3 (Tomás in a game every time) |

The same week is also the ninth week of each of the four routing runs above (memory on, the RTX 3090): Tomás was in
none of its games in any of them, with routing off or on (`submission/results/autopilot_eval_route*.json`).

## Reproduce

On the GPU server, in `agent/`:

```bash
node test/scale_eval.mjs data/scale_eval.json        # the tables above (about 15 minutes)
node test/scale_chart.mjs data/scale_eval.json ../docs/scale.svg
node test/persona_eval.mjs data/persona_eval.json    # the rules, both arms (about 15 minutes)
node test/load_eval.mjs data/load_eval.json          # one GPU, many players (about 15 minutes)
node test/private_eval.mjs data/private_eval.json    # private calendars, a usual week (about 10 minutes)
PRIVATE_WEEK=all node test/private_eval.mjs data/private_eval_all.json   # and a week free every day
node test/contention_eval.mjs data/contention_eval.json   # two talks at once, holds off and on (about 13 minutes)
EVAL_A2A=1 node test/contention_eval.mjs data/contention_eval_a2a.json   # the same over A2A
node test/memory_eval.mjs data/memory_eval.json   # memory: retrieval alone (DRAMA on the CPU)
EVAL_A2A=1 EVAL_ONLY="Tomás" EVAL_REPEAT=3 node test/autopilot_eval.mjs data/autopilot_eval_memory_on.json   # and MEMORY=off
```
